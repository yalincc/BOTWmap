# xnavi v3.2.1 版本报告（2026-10-23）

## 1. 版本概述

v3.2.1 有三块内容：**GUI 存档统计补齐到与网页面板一致的 18 项**（核心自己读存档，不依赖网页）、**定位成功后打开在线地图的改造**（原来参数被丢弃、落到本地引导页）、以及三件收尾治理（旧状态导致误开图、发布包垃圾、一处与实现相反的文档）。界面侧另做了 18 项排版与定位按钮三态。

| 项 | 内容 |
|---|---|
| 版本号 | `xnavi-v3.2.1`（导航程序独立版本，与网页版解耦） |
| 上一版 | `xnavi-v3.2.0`（2026-10-22，管道化架构重构） |
| 发布包 | `RELEASE/xnavi-v3.2.1.zip`（7.93MB / 13 项，纯净版）+ `RELEASE/xnavi-v3.2.1-BOTWmap-package.zip`（57.09MB / 11197 项，含完整 `app/` 离线地图，支持手机局域网扫码导航） |
| 破坏性变更 | 无（命令行参数、接口、配置格式全部兼容；`status.json` 仅新增字段） |

### 与 v3.2.0 的源码关系（重要）

v3.2.0 的 tag 指向的源码包含 3 处**发布后才做、未重建二进制**的收尾微调（tag 注解已注明）：

1. 移除 GUI 启动时物理删除 `status.json` 的动作；
2. 简化自动开图门禁（去掉多余的 `coreRunning` / `ok` 前置判断，保留 `verified`）；
3. config 指针型字段默认值补全（`autoOpenMap` / `autoDetectSave`）。

这三处在 v3.2.1 中正式构建并交付。因此：**v3.2.1 的二进制 = v3.2.0 的 tag 源码 + 本报告的改动**。

## 2. 新增：存档统计补齐 18 项

### 2.1 做了什么

GUI 原本只显示 5 项（神庙 / 高塔 / 克洛格 / 回忆 / 神兽），其余 12 项一直依赖网页端 `/save` 管道解析。本版让**核心自己把 18 项全部算出来**，界面一次排满四组：

| 组 | 项 | 分母 |
|---|---|---|
| 探索 | 神庙 / 高塔 / 神兽 / 克洛格 / 照片记忆 / 最终回忆 | 136 / 15 / 4 / 900 / 12 / 1 |
| 任务 | 主线挑战 / 支线任务 / 神庙挑战 / DLC 任务 | 15 / 77 / 42 / 19 |
| 收集 | 宝箱 / 武器获得 / 图鉴·装备 / 图鉴·材料 / 图鉴·怪物 | 1312 / 196 / 179 / 112 / 84 |
| 讨伐 | 西诺克斯 / 岩石巨人 / 莫尔德拉吉克 | 43 / 44 / 5 |

> 任务 4 项的分母按网页面板的 `inRow()` 规则计算：DLC 任务（含 collabo 联动）占 DLC 行，本体三行的分母因此是 15/77/42，而非数据总表的 20/90/42。

### 2.2 为什么不用「把网页 JS 搬进 GUI」

`save_upload.js` 与地图、画布、localStorage 深度耦合，搬进 GUI 需要先做手术，反而更高风险；而「计数」根本不需要网页那几 MB 的点位数据。

核心只需要 hash 集合：新增 `source/build_save_stats.py` 从现有网页字典派生 `xnavi/data/save_stats.json`，**23KB**，`go:embed` 内嵌。

### 2.3 讨伐 3 项为什么不需要坐标

网页用「点位就近匹配」归族，是为了同时给地图打勾。计数场景下不需要：92 条 `IsDefeat_Enemy_*` 的 flag 名自带种族名——`_Giant_` = 西诺克斯、`_Golem_` = 岩石巨人、`_Sandworm_` = 莫尔德拉吉克（含 `SandwormR` 等变体）。按前缀归族即可。

生成脚本与 `enemy_save.js` 交叉验证：**两边各 92 条、交集 92 条，完全一致**。

### 2.4 口径差异

- **探索 6 / 收集 5 / 讨伐 3（14 项）**：网页统计面板本身就是「存档优先」（`renderStats()` 里存档数据优先于本地勾选集），两边数字一致；
- **任务 4 项**：网页的 `QuestDone.isDone` 会把手动勾选算进去，若用户手动勾过任务，网页可能略高。界面已注明「仅统计存档数据」。

## 3. 改造：定位成功后打开在线地图

### 3.1 原来的问题（三层）

| 层 | 现象 | 根因 |
|---|---|---|
| 1 | 前端算好的地址没生效 | `api.OpenMapURL(url)` 对应的 Go 方法是**无参**的 `OpenMapURL()`，Wails 绑定为 `OpenMapURL():Promise<string>`，传入的 url 被静默丢弃 |
| 2 | 打开的是本地地址 | 后端只有两个选项：`customMapURL` 非空用它，否则兜底 `http://127.0.0.1:8766`；默认配置里 `customMapURL` 为空 |
| 3 | 打开后没有地图 | 发布包不含 `app/`，核心对 `/` 与 `/botw/` 直接返回内置引导页（`server.go` 的 `writeMirrorFallback`），用户看到一段说明文字而非地图 |

附带一层隐藏缺陷：即使把参数接上，旧实现走命令行 start，URL 里的 `&` 会被当分隔符截断，`?follow=1&game=botw` 会被砍掉。

### 3.2 改造方式（做减法）

- 地址**写死** `https://botw.yalin.site/?follow=1&game=botw`（前端常量 `MAP_URL`；xnavi 只服务 BOTW，不做自定义地址）。
- 打开方式改 `rt.BrowserOpenURL(MAP_URL)` —— Wails 自带，走系统 ShellExecute，不经命令行解释器，`&` 不会被截断。
- `follow=1` 的消费方是网页 `app/js/live.js:43`：命中即把跟随置为开启并写入 localStorage（持久化）。
- 删除清单：`Config.CustomMapURL`、Go 的 `OpenMapURL()`、前端 `buildMapUrl / defaultMapUrl / statusMapUrl`、设置面板自定义网址输入框、两条中英文案、wailsjs 两条绑定。
- 保留：主横幅【打开地图】手动入口；自动开图仍严格等待 `verified=true`。

### 3.3 遗留（转网页侧，已入待办池）

从 xnavi 打开地图后，跟随只把视图居中、缩放停在网页初始值（用户手动放大到的档位刷新即丢失）。根因在网页 `live.js:327` 的 `Math.max(map.view.scale, 0.55)` —— 只往上抬、不恢复上次值。已记入 `docs/backlog/BACKLOG.md` 候选池，按网页发版流程单独排期。

## 4. 修复：状态快照会话签名

### 4.1 问题本质

`status.json` 是核心每 2 秒覆盖写的**运行快照**（不是启动配置；启动配置在 `xnavi-gui-config.json`）。程序退出时这个文件留在磁盘上，没人清理。

下次启动时，界面侧的 800ms 轮询会在核心写出第一份新快照之前（最长 2 秒）先读到磁盘上残留的旧快照，其中带着**上次会话的坐标**与 `verified=true`。界面据此判定「已锁定」，按门禁规则自动呼出地图——红点停在上次的位置。

### 4.2 曾经的处理方式（已废弃）

v3.2.0 初期采用「启动核心前第一件事：物理删除 `status.json`」。这是掩盖症状而非识别身份：

- 删文件属于无条件破坏，谁写的、新不新一概不问；
- 若核心由 GUI 之外的方式启动（命令行调试），删除动作不存在，问题原样复现；
- 删除与写入之间存在竞态窗口（核心可能刚写完就被删）。

### 4.3 现行做法：给快照签会话身份

| 端 | 改动 | 位置 |
|---|---|---|
| 核心 | 快照新增 `corePid`（**核心自身**进程号），与既有 `pid`（所附加的**模拟器**进程号）明确区分 | `xnavi/monitor.go` `statusLoop()` |
| 界面 | `StartCore` 成功后记录子进程 PID；`CoreStatus()` 读快照后校验 `corePid` 是否等于本次拉起的子进程号 | `xnavi-gui/app.go` |
| 界面 | 校验不过 → **整条丢弃**，强制 `ok=false / verified=false`，状态显示「核心启动中，等待本次会话首份状态」；核心未运行时一律不改用磁盘快照 | `xnavi-gui/app.go` `snapshotSignedBy()` |
| 界面 | 未取得签名快照时清空「最新存档」相对时间，避免残留上次的「X 小时前」 | `xnavi-gui/frontend/src/composables/useCore.js` |

### 4.4 为什么不用时间戳判据

快照里本来就有 `time` 字段（RFC3339），「时间戳方案」看似零改动：界面记下本次拉起核心的时刻，比快照时间更新就采纳。否决理由：

| 判据 | 依赖 | 失效场景 |
|---|---|---|
| 时间戳 | 系统时钟 | 用户改系统时间、切时区、笔记本休眠唤醒后时钟跳变；且 GUI 反复启停核心时基准时刻需同步刷新 |
| 进程身份（采用） | 进程号唯一性 | 新核心恰好复用旧核心 PID（概率极低，且要求旧快照正来自该号） |

两者实现成本相同，**时间会被改、进程号不会**，故选身份。

### 4.5 三层防护的最终形态

| 层 | 位置 | 作用 |
|---|---|---|
| L1 网页端退避 | `app/js/live.js`（`failCnt >= 3` → 停轮询 + 30s 退避） | 兜底：即使前端读到不可用接口，也不会无限重试烧资源 |
| L2 开图门禁 | `useCore.js` `setStepState()`：`verified === true` 才呼出浏览器 | 初锁候选点（`verified=false`）保持静默，不抢跑 |
| L3 会话签名（本版新增） | 核心写 `corePid` + 界面比对 | 从源头杜绝「上次会话的旧快照被当成本次状态」 |

## 6. 文档纠正：Ryujinx 定位机制

### 6.1 错在哪

`CHANGELOG.md` 的 v3.2.0 条目原写：

> `watch_ryujinx.go`：专属 Switch 小端固定偏移秒读（`0xA77FCBBC`），零扫描，死守锁定的 addr

**与实际实现相反**。代码自 v3.2.0 起已改为动力学根运动缓冲扫描，版本报告中亦正确记载了「废除该偏移」。

### 6.2 实际机制（已核对代码）

1. **未锁定**：每秒一次，遍历 ≥256MB 的 guest 内存块，切 8MB 分片、4 线程并发读取；
2. `FindEdenTriples()` 每 4 字节滑窗读 3 个 float32 作为坐标，过 `WorldCoordOK()` 合法性判断；
3. 以**最新存档位置**为圆心，保留 ±120m 窗口内的命中（未命中依次放大到 400m、3000m；手工校准时为 ±150m）；
4. 该坐标后随 12 字节必须是**单位四元数**（`IsQuatUnit`）才计入 `Run` —— 这是运动对象的特征结构；
5. **`Run >= 2` 硬门禁**：真身是 32~33 个连续槽的 RingBuffer，静态数据与外观 Transform 槽连不成串；
6. 多组候选按就近取优锁定，此后死守该地址；走动 0.5m 以上仲裁确认真身 → `verified=true`。

### 6.3 为什么不能用固定偏移

`0xA77FCBBC` 指向的是**外观骨骼 Transform 槽**，不是动力学根对象。骑乘 / 盾滑 / 骑摩托时该槽被引擎复用为标志位，读出 `(0, 1, Z)` 之类的退化向量，与上一帧产生数百米突跳，误触发 `[warp]`。

它当年可用，是因为 Ryujinx 的内存块基址相对稳定，「块基址 + 常量」能直接命中；**但命中的对象本身是错的，地址再稳也拿不到正确坐标**。

### 6.4 固定偏移的残留

仅 `xnavi/main.go` 启动时「猜这次是不是 BOTW」的探测仍列出该偏移（`botwOffs`）。程序只服务 BOTW，猜不出也会兜底成 BOTW，故该探测不影响功能，属历史残留，本版未动。

## 9. 待实机验证（发版门禁）

1. 正常启动 → 锁定 → 走动几步 → 地图正好在 `verified=true` 那一刻弹出，红点即真实位置；
2. 上次会话遗留 `status.json`，重启 GUI → 首 2 秒界面显示「核心启动中」，地图不提前弹出；
3. 点「停止」再点「开始」→ 快照重新签名，相对时间从「刚刚」重新起算，不显示上次的旧值；
4. 暂停核心（关 GUI 留核心）再重开 GUI → 界面不显示上次会话的坐标（核心未由本次 GUI 拉起，无签名）；
5. **18 项面板**：开始定位后，右侧「本地解析进度」应完整显示四组 18 项，数字非 `-`；把同一存档拖进网页，逐项对照 14 项（探索/收集/讨伐）应完全一致，任务 4 项若手动勾过会略有差异；
6. **换档实时刷新**：游戏内存盘后，宝箱/任务等数字应随存档 mtime 变化自动更新，无需重启；
7. **Cemu（大端）**同样验证一份存档，确认字节序识别无误。
