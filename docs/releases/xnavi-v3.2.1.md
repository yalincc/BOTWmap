# xnavi v3.2.1 版本报告（2026-10-23）

## 1. 版本概述

v3.2.1 是 v3.2.0 交付后的**收尾治理版**，不新增功能，只解决三件事：一个真实缺陷（旧状态导致误开图）、一批不该进包的垃圾、一处与实现相反的错误文档。

| 项 | 内容 |
|---|---|
| 版本号 | `xnavi-v3.2.1`（导航程序独立版本，与网页版解耦） |
| 上一版 | `xnavi-v3.2.0`（2026-10-22，管道化架构重构） |
| 发布包 | `RELEASE/xnavi-v3.2.1.zip`（纯净版，不含任何运行时产物） |
| 破坏性变更 | 无（命令行参数、接口、配置格式全部兼容） |

### 与 v3.2.0 的源码关系（重要）

v3.2.0 的 tag 指向的源码包含 3 处**发布后才做、未重建二进制**的收尾微调（tag 注解已注明）：

1. 移除 GUI 启动时物理删除 `status.json` 的动作；
2. 简化自动开图门禁（去掉多余的 `coreRunning` / `ok` 前置判断，保留 `verified`）；
3. config 指针型字段默认值补全（`autoOpenMap` / `autoDetectSave`）。

这三处在 v3.2.1 中正式构建并交付。因此：**v3.2.1 的二进制 = v3.2.0 的 tag 源码 + 本报告的改动**。

## 2. 修复：状态快照会话签名

### 2.1 问题本质

`status.json` 是核心每 2 秒覆盖写的**运行快照**（不是启动配置；启动配置在 `xnavi-gui-config.json`）。程序退出时这个文件留在磁盘上，没人清理。

下次启动时，界面侧的 800ms 轮询会在核心写出第一份新快照之前（最长 2 秒）先读到磁盘上残留的旧快照，其中带着**上次会话的坐标**与 `verified=true`。界面据此判定「已锁定」，按门禁规则自动呼出地图——红点停在上次的位置。

### 2.2 曾经的处理方式（已废弃）

v3.2.0 初期采用「启动核心前第一件事：物理删除 `status.json`」。这是掩盖症状而非识别身份：

- 删文件属于无条件破坏，谁写的、新不新一概不问；
- 若核心由 GUI 之外的方式启动（命令行调试），删除动作不存在，问题原样复现；
- 删除与写入之间存在竞态窗口（核心可能刚写完就被删）。

### 2.3 现行做法：给快照签会话身份

| 端 | 改动 | 位置 |
|---|---|---|
| 核心 | 快照新增 `corePid`（**核心自身**进程号），与既有 `pid`（所附加的**模拟器**进程号）明确区分 | `xnavi/monitor.go` `statusLoop()` |
| 界面 | `StartCore` 成功后记录子进程 PID；`CoreStatus()` 读快照后校验 `corePid` 是否等于本次拉起的子进程号 | `xnavi-gui/app.go` |
| 界面 | 校验不过 → **整条丢弃**，强制 `ok=false / verified=false`，状态显示「核心启动中，等待本次会话首份状态」；核心未运行时一律不改用磁盘快照 | `xnavi-gui/app.go` `snapshotSignedBy()` |
| 界面 | 未取得签名快照时清空「最新存档」相对时间，避免残留上次的「X 小时前」 | `xnavi-gui/frontend/src/composables/useCore.js` |

### 2.4 为什么不用时间戳判据

快照里本来就有 `time` 字段（RFC3339），「时间戳方案」看似零改动：界面记下本次拉起核心的时刻，比快照时间更新就采纳。否决理由：

| 判据 | 依赖 | 失效场景 |
|---|---|---|
| 时间戳 | 系统时钟 | 用户改系统时间、切时区、笔记本休眠唤醒后时钟跳变；且 GUI 反复启停核心时基准时刻需同步刷新 |
| 进程身份（采用） | 进程号唯一性 | 新核心恰好复用旧核心 PID（概率极低，且要求旧快照正来自该号） |

两者实现成本相同，**时间会被改、进程号不会**，故选身份。

### 2.5 三层防护的最终形态

| 层 | 位置 | 作用 |
|---|---|---|
| L1 网页端退避 | `app/js/live.js`（`failCnt >= 3` → 停轮询 + 30s 退避） | 兜底：即使前端读到不可用接口，也不会无限重试烧资源 |
| L2 开图门禁 | `useCore.js` `setStepState()`：`verified === true` 才呼出浏览器 | 初锁候选点（`verified=false`）保持静默，不抢跑 |
| L3 会话签名（本版新增） | 核心写 `corePid` + 界面比对 | 从源头杜绝「上次会话的旧快照被当成本次状态」 |

## 3. 清理：发布包纯净与死代码

### 3.1 删除 `xnavi/diagnostic.go`

该文件内的 `dumpDiagnostic()` 在 v3.2.0 中**已无任何调用点**（死代码）；`--dump` 调试模式走的是另一个函数 `dumpDiagnostics()`（`main.go`）。此前发布包内 11 个 `diagnostics/diag_*.json` 均为 3.1.x 时期锁定后自动 dump 的残留（实测内容仅 278 字节，`nearby_pointers` / `pointers_to_player` 全为 null）。

删除后：**不会再产生新的诊断垃圾**，`--dump` 调试能力不受影响。

### 3.2 `.gitignore` 补齐

| 新增规则 | 原因 |
|---|---|
| `xnavi-gui/xnavi-core.exe` | 7.9MB 核心副本，此前出现在未跟踪列表，`git add -A` 会误入库 |
| `xnavi-gui/diagnostics/` | 运行时诊断目录 |
| `xnavi-gui/status.json` / `*.log` / `xnavi-gui-config.json` | 运行时产物与含本机路径的配置 |

### 3.3 发布包规范落地

`RELEASE/README.md` 新增「发布包目录规范」：必带 7 项（exe ×2、`data/`、`certs/`、README、TROUBLESHOOTING、icon）、禁带 6 类（`status.json`、日志、GUI 配置、`diagnostics/`、`known_botw_cemu.json`、留底文件），并固定四步出包自检（列清单 / SHA 一致 / 图标 MATCH / 空目录试跑）。

## 4. 文档纠正：Ryujinx 定位机制

### 4.1 错在哪

`CHANGELOG.md` 的 v3.2.0 条目原写：

> `watch_ryujinx.go`：专属 Switch 小端固定偏移秒读（`0xA77FCBBC`），零扫描，死守锁定的 addr

**与实际实现相反**。代码自 v3.2.0 起已改为动力学根运动缓冲扫描，版本报告中亦正确记载了「废除该偏移」。

### 4.2 实际机制（已核对代码）

1. **未锁定**：每秒一次，遍历 ≥256MB 的 guest 内存块，切 8MB 分片、4 线程并发读取；
2. `FindEdenTriples()` 每 4 字节滑窗读 3 个 float32 作为坐标，过 `WorldCoordOK()` 合法性判断；
3. 以**最新存档位置**为圆心，保留 ±120m 窗口内的命中（未命中依次放大到 400m、3000m；手工校准时为 ±150m）；
4. 该坐标后随 12 字节必须是**单位四元数**（`IsQuatUnit`）才计入 `Run` —— 这是运动对象的特征结构；
5. **`Run >= 2` 硬门禁**：真身是 32~33 个连续槽的 RingBuffer，静态数据与外观 Transform 槽连不成串；
6. 多组候选按就近取优锁定，此后死守该地址；走动 0.5m 以上仲裁确认真身 → `verified=true`。

### 4.3 为什么不能用固定偏移

`0xA77FCBBC` 指向的是**外观骨骼 Transform 槽**，不是动力学根对象。骑乘 / 盾滑 / 骑摩托时该槽被引擎复用为标志位，读出 `(0, 1, Z)` 之类的退化向量，与上一帧产生数百米突跳，误触发 `[warp]`。

它当年可用，是因为 Ryujinx 的内存块基址相对稳定，「块基址 + 常量」能直接命中；**但命中的对象本身是错的，地址再稳也拿不到正确坐标**。

### 4.4 固定偏移的残留

仅 `xnavi/main.go` 启动时「猜这次是不是 BOTW」的探测仍列出该偏移（`botwOffs`）。程序只服务 BOTW，猜不出也会兜底成 BOTW，故该探测不影响功能，属历史残留，本版未动。

## 7. 待实机验证（发版门禁）

1. 正常启动 → 锁定 → 走动几步 → 地图正好在 `verified=true` 那一刻弹出，红点即真实位置；
2. 上次会话遗留 `status.json`，重启 GUI → 首 2 秒界面显示「核心启动中」，地图不提前弹出；
3. 点「停止」再点「开始」→ 快照重新签名，相对时间从「刚刚」重新起算，不显示上次的旧值；
4. 暂停核心（关 GUI 留核心）再重开 GUI → 界面不显示上次会话的坐标（核心未由本次 GUI 拉起，无签名）。
