# Enavi —— Eden / 旷野之息 只读实时大地图伴侣

给 `https://botw.yalin.site` 喂坐标的本地小服务：在 Eden 里玩《旷野之息》时，
把林克的 **X / alt / Z** 实时推到地图上，并联动附近的神庙与克洛格。
（朝向不输出 —— 前端 `live.js` 已用位移推算箭头并做最短弧平滑，老大定的，精度够用且更稳。）

完整方案：[`PLAN.md`](./PLAN.md)

## 三条红线

1. **纯只读**：只申请 `PROCESS_VM_READ`，不写内存、不注入、不改存档；
2. **不碰网页**：Enavi 只提供 HTTP 数据，`app/` 一行不改（协议 v1 与现有前端兼容）；
3. **不依赖 Eden 调试功能**：生产路径只用 `ReadProcessMemory`。
   （实测 Eden 0.2.1 的 GDB Stub 残缺 —— 开启后游戏会卡在加载画面，只能当事故排查工具。）

## 定位原理（2026-10-20 实测定案）

Enavi 读的是**游戏自己维护的玩家位置历史缓冲** —— 不是猜的，是逆出来的：

```
每个元素 0x28（40）字节：
  +0x00  Vector3f 位置 (X, alt, Z)   ← 只要这 12 字节
  +0x0C  朝向四元数 w ∈ (0.90, 1.00)
  +0x10  x ∈ (-0.5, 0.5)
  +0x14  y ∈ (-0.5, 0.5)
  +0x18  朝向角（单位：度）
```

启动时扫一次内存，用「**四元数指纹 + 合法世界坐标**」把这个数组找出来
（实测加指纹后命中从 1457 万降到几千，但仍需「会变验证」才能认出玩家），
之后每 100ms 死读 12 字节。

**为什么这样最稳**：
- 坐标是**实时**的，不是存档里的旧值 → 传送后立刻正确；
- 不依赖存档 → 玩家没存档也能定位；
- 玩家站着不动时保留最后位置，不会归零或乱跳；
- 定位一次就写盘 → 下次启动**直接读地址，零扫描**。

## 老实说：它和 xnavi 的关系

**方法上是同一类** —— 都是「扫内存认坐标槽」。Enavi 没有跳出这个框，
老大一开始要的是「基址 + 固定偏移」（跨会话不变），**那个没做成**（详见 PLAN.md §14）。

**唯一的实质差别是稳定性**：

| | xnavi | Enavi |
|---|---|---|
| 定位方法 | 扫描 | 扫描（同类） |
| 状态机 | 探针池 / 候选分级 / 半死槽换锁 / 乒乓淘汰 / 失败组登记 | **只有 3 条失效规则** |
| 参数化机制 | 一大堆 | 无（采样频率写死） |
| 朝向解算 | 有 | 无（前端位移推箭头） |

老大嫌 xnavi「bug 没断过」，根因是机制太多互相打架。
Enavi 的价值是**用极简状态机把这类 bug 的土壤去掉**，不是方法更新。

### 已知限制（不瞒）

1. **每次重开 Eden 要重新定位一次**（十几秒）—— 坐标槽地址随会话变，这是扫描类的宿命
2. **定位时需要在游戏里走动** —— 靠「位置明显移动」区分玩家和 NPC 位置表（站着不动时认不出，这是设计取舍：宁可显示"定位中"，也不返回一个假坐标）
3. **Eden 不重启时，重启服务能秒读缓存**（`known_player.json`）

## 为什么它比 xnavi 稳

xnavi 的 bug 不是算法不聪明，而是**机制太多互相打架**（探针池、半死槽换锁、候选分级、乒乓淘汰…）。
Enavi 只留三件事：

1. **锁定就写盘**（`known_player.json`，带 pid + Eden 启动时间）→ 下次启动**直接读地址，不扫描**；
2. **只有三种明确失效才重扫**：连续 5 次读失败 / 单拍跳变 >300m / 进神庙本地尺度；
3. **重扫 = 重新定位那个缓冲**，不做候选排名试探、不换锁。

站着不动、跑动、骑马、开菜单 —— **一律不重扫、不换锁**。

> 朝向不做：网页地图只需要坐标，前端 `live.js` 已用位移推算箭头并做了最短弧平滑，精度够用且更稳。

## 日常使用：双击 `M1.bat`

双击后它会：
1. 起一个只读的定位服务（`127.0.0.1:8766`）；
2. 自动打开 `https://botw.yalin.site/?follow=1&game=botw`；
3. 地图上的红点就开始跟林克走，转身时会带方向。

首次启动要扫一次内存定位（十几秒）；之后启动直接读缓存，**秒开**。
红点不动 / 显示"定位中"时：在游戏里**走两步**（定位靠「位置会变」来确认是玩家，不是 NPC 位置表），
或者关掉重开。窗口别关，关了服务就停了。

## 体检模式：双击 `M0.bat`

**双击 `M0.bat`**，跟着窗口里的提示走就行：

1. 它先等你把游戏跑起来（进游戏、读到存档、人物能走动）；
2. 然后自动测内存布局、找身份锚点；
3. 中间会让你回游戏里**走 10 秒**，回来按一次 Enter；
4. 最后自动打开 `report\` 文件夹，把那个 `M0-时间.log` 发回来即可。

全程只有"在游戏里做动作 + 按 Enter"两类操作，不用改 Eden 任何设置。
想中止：输 `q` 再回车。

| 步骤 | 测什么 | 为什么重要 |
|---|---|---|
| 1 | 等进入游戏 | 空载时 User Heap 是空的，测什么都是空的 |
| 2 | DRAM 大块 / User Heap 形态 | 决定 ASLR 怎么反解、扫描范围多大 |
| 3 | `Player` / `GameROMPlayer` / `1.6.0` 字符串 | 决定"身份锚点"这条路成不成（要排除 romfs 干扰） |
| 4 | 走动采样（无锚点找玩家槽） | 不用坐标就能指认玩家槽，是 M1 冷启动的关键 |
| 5 | 候选邻域的四元数 → 朝向 | 决定箭头能不能直接读出来 |
| 6 | GDB Stub 探测 | 只为证明它不能当实时通道；没开就跳过 |

分项命令、每项判据、台账表格见 `PLAN.md` §5。

## 目录

| 路径 | 作用 |
|---|---|
| **`M0.bat`** | M0 实机体检（采集平台事实，产出日志给我） |
| **`M1.bat`** | **直接开跑：启动定位服务 + 自动打开地图**（日常用这个） |
| `cmd/enavi/` | 定位服务：10Hz 跟随 + `GET /pos`（协议 v1，前端零改动） |
| `internal/locate/` | 定位核心：known 秒锁 → 死读一个地址 → 三种明确失效才重扫 |
| `internal/known/` | 地址缓存（`known_player.json`），同一次 Eden 会话内有效 |
| `internal/saveanchor/` | 存档解析：坐标 + 心/体力值（冷启动锚点） |
| `cmd/enavi-probe/` | M0 探针：进程 / DRAM / 区域 / 字符串 / 坐标 / 结构 / GDB |
| `internal/winmem/` | 只读内存层：进程枚举、区域遍历、DRAM 反解、带重试读取 |
| `internal/scan/` | 坐标三元组、旋转矩阵、四元数→朝向、分组排序 |
| `internal/gdbstub/` | 最小 RSP 客户端（仅 M0 验证用） |
| `data/progress_points.json` | POI：1078 点（神庙 136 / 塔 15 / 神兽 4 / 克洛格 900 / 回忆 23），**像素坐标** |
| `profiles/botw_eden.json` | Eden 平台事实登记：锚点阶梯、身份判据、阈值、M0 结论 |
